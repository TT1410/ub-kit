# ub-kit

Метод Роберта Мартіна (жовтень 2026), який ставиться в будь-який репозиторій однією командою:
- одна задача — один дисциплінований агент зі скілом `ub-mode`;
- детерміновані ворота з інструментів Мартіна: crapper, dryer, mutator і uml-viewer;
- рецензія іншою моделлю;
- людина перевіряє поведінку руками і погоджує злиття.

Kit нічого не знає про вашу архітектуру. Він міряє код на Python, Go чи TypeScript, а шари й межі задаєте ви.

## Швидкий старт

```bash
git clone https://github.com/TT1410/ub-kit ~/ub-kit          # один раз на машину; оновлення: git -C ~/ub-kit pull
~/ub-kit/install.sh ~/Projects/my-repo                       # наявний репозиторій, новий або порожня тека
cd ~/Projects/my-repo && claude                              # далі в Claude Code: /ub-setup
```

У спільному проєкті kit ставить одна людина й комітить `.ub/` та `.claude/`. Решта команди отримує все разом із репозиторієм; кожному лишається встановити залежності — `.ub/ub doctor` покаже, чого бракує.

**`install.sh`** визначає й записує:
- мови та їхні корені;
- головну гілку;
- команду verify;
- режим.

Чого визначити не може, позначає `TODO(ub-setup)`. Ще він дописує блок у `AGENTS.md`/`CLAUDE.md`, правила «спитати власника» в `.claude/settings.json` і рядки в `.gitignore`. Нічого не комітить. Ключ `--dry-run` лише показує, що зміниться.

**`/ub-setup`** — скіл, який агент виконує разом із вами один раз:
- **новий проєкт:** питає мову, стек і шари й ставить мінімальний каркас під вашу відповідь;
- **наявний проєкт:** налаштовує verify і межі модулів, підключає плагін для vitest, записує шари на діаграмі й базову лінію боргу;
- **наприкінці** проганяє ворота на пробній зміні.

### Цикл кожної задачі

1. Ви ставите задачу. Агент працює за `ub-mode` на гілці задачі.
2. `.ub/ub gate` має бути зеленим. Агент сам повторює його, доки не стане зеленим.
3. `.ub/ub review`: інша модель читає дифф. Агент відповідає на кожне зауваження.
4. Ви перевіряєте поведінку — приймальними тестами (`[ub] acceptance`) або руками — і читаєте критичний код: гроші, безпеку.
5. Злиття. Push — лише за вашим словом.

Перед релізом — проходи за аспектами, як у Мартіна (8 листопада): `.ub/ub audit architecture`, `coverage`, `concurrency`, `security`, `api`. Інша модель перевіряє не кожен рядок, а те, чим цей аспект доведено: тести, перевірки, інструменти. Чеклісти лежать у `.ub/audits/`.

Файли kit перезаписує `install.sh --upgrade <repo>`. Файли проєкту він не чіпає.

Самі інструменти лежать поза репозиторієм, у спільному кеші `~/.cache/ub-kit/`. Їх клонують один раз на всі проєкти, на закріплених комітах:
crapper, mutator, dryer і uml-viewer — усі у Мартіна. З 10 листопада його uml-viewer сам читає Go, а crapper і mutator знаходять покриття Go за шляхом модуля з go.mod, тож форк і обхід зі шляхами в kit більше не потрібні.

## Ворота (`.ub/ub gate [BASE]`)

Ворота судять тільки те, що змінилося від merge-base з головною гілкою, разом із незакоміченими файлами. Етапи:
1. **verify** — lint, типи, межі модулів, тести: команда з `.ub/config`.
1a. **acceptance** — приймальні тести, погоджені з власником (AgNesse, FitNesse, Gherkin…), якщо задано `[ub] acceptance`. Модульні тести, «насичені» crapper і mutator, тримають код стабільним; що система робить правильну річ, показують ці тести або людина.
2. **CRAP < 10** для функцій змінених файлів (crapper). Покриття беруть з тестів змінених пакетів чи модулів.
3. **Дублікати** з подібністю ≥ 0,8, що зачіпають зміну (dryer).
4. **Мутанти** не мають ні виживати, ні лишатися непокритими (mutator). Якщо змінилися тести, повністю мутується й код, який вони тестують. Мутант, якого раніше вбивали, а тепер він виживає, — завжди червоне. Знімок для порівняння береться з коміту бази, тож повторний запуск це не «відмиє».
5. **Dependency Rule** на діаграмі uml-viewer, якщо є політика, Java 21 і Clojure.

Ворота падають «закрито»: якщо інструмент упав, не дав звіту або нема чого судити — це червоне. `GATE_SKIP=verify,acceptance,crap,dry,mutation,structure` пропускає етапи, але це записується в `.ub/out/gate/summary.txt`, і рецензент це бачить.

### Режими

- **strict** — для нових проєктів. Усе у змінених файлах має бути чистим.
- **ratchet** — для наявних проєктів. Червоне лише нове:
  - мутанти на змінених рядках;
  - дублікати, що зачіпають змінені рядки;
  - функції з CRAP ≥ 10, яких немає в базовій лінії або які погіршилися.

  Старий борг у зачеплених файлах іде у звіт рядками `DEBT:` і не блокує. Агент має лишити його меншим, ніж знайшов. Базову лінію записує `.ub/ub baseline`, з вашого дозволу.

Нові проєкти (до 15 файлів коду) отримують strict, решта — ratchet. Режим змінюється в `.ub/config`.

## Налаштування (`.ub/config`)

| Ключ | За замовчуванням | Що задає |
|---|---|---|
| `[ub] main` | визначається | гілка, від якої рахується зміна |
| `mode` | strict / ratchet | див. вище |
| `verify` | визначається (`just verify`, `make check`, скрипт пакета або ланцюжок команд) | lint, типи, межі, тести, з кореня репозиторію |
| `acceptance` | — | команда приймальних тестів; порожньо — поведінку перевіряє людина |
| `crap_max`, `dry_threshold` | 10, 0.8 | пороги Мартіна |
| `exclude` | — | regex шляхів, які ворота не судять (згенерований код без заголовка «do not edit») |
| `structure` | auto | `off` вимикає етап діаграми |
| `workers` | 4 | паралельні мутанти на файл |
| `mutation_wrap` | — | обгортка для запусків mutator, напр. машинна черга важких прогонів (`./infra/heavy/run.sh`) |
| `mutation_jobs` | 2 | скільки файлів мутується одночасно (після одного спільного прогону покриття) |
| `reviewers` | `grok codex` | порядок рецензентів. Якщо один не відповів, пробується наступний. `claude` — лише коли автор не Claude |
| `[python] root`, `src`, `test`, `coverage`, `setup` | | корінь, вихідний код, команди mutator і crapper, підготовка (наприклад, тестова БД) |
| `[go] root`, `src`, `tree`, `test`, `setup` | | `tree` — regex: група 1 — тека, чиї тести судять файл (модуль цілком) |
| `[typescript] root`, `src`, `setup` | | лише vitest |

## Мови

- **Python.** crapper і mutator самі запускають pytest із покриттям через `.venv`. Проєкт **не можна** ставити в `.venv` як editable: тоді тести бачать оригінал, а не копію mutator, і всі мутанти «виживають». З uv це `[tool.uv] package = false` плюс pytest `pythonpath = ["src"]`. `.ub/ub doctor` перевіряє це.
- **Go.** Покриття змінених пакетів. Шляхи у профілі переписуються з імені модуля на теку, тож модуль може називатися інакше, ніж його тека. Тести з БД запускаються через `[go] setup`.
- **TypeScript.** vitest і `@vitest/coverage-v8`. Специфікація лежить поруч із модулем (`name.spec.ts`, `name.test.ts` або `__tests__/`). У конфіг vitest треба вставити плагін `.ub/snippets/vitest-mutator-overlay.ts.txt`: Vite іде за симлінками mutator до оригіналу. Без плагіна ворота червоні з поясненням. vitest запускається власним бінарником, а не через `pnpm exec`: менеджер пакетів у копії mutator може перевстановлювати залежності й «вбивати» кожного мутанта.

## Вимоги

- git і Python ≥ 3.9 для kit; Python ≥ 3.11 на PATH для інструментів Мартіна;
- just — не потрібен. Команди — `.ub/ub gate`, `.ub/ub review`… (Windows: `py .ub\ub gate`). Якщо в проєкті вже є justfile, інсталятор додає `import '.ub/ub.just'`, і працює `just gate` (вимкнути: `--no-just`);
- для своїх мов — uv, poetry чи pip; go; node з менеджером пакетів;
- для діаграми — Java 21 і Clojure CLI;
- для рецензії — Grok із кредитами або Codex після `codex login`.

`.ub/ub doctor` показує, чого бракує.

## Обмеження

- Ворота судять один корінь на мову. Якщо в монорепозиторії знайшлося кілька, інсталятор їх перелічує.
- `.vue`, `.svelte` і Gherkin ворота не судять. Їх перевіряє лише verify.
- mutator тримає знімок Go по одному на пакет. Регресію ослабленого тесту ворота ловлять для файлу, який мутувався останнім.
- Функція без розгалужень і без місць для мутацій (наприклад, `return f(100, 10)`) проходить ворота навіть без жодного тесту: CRAP для CC = 1 не перевищує 2, а мутувати нема чого. Так влаштовані метрики Мартіна; такі місця ловить `.ub/ub audit coverage` і приймальні тести.
- Фальшиві «вбивства» можливі, якщо тест падає з причин, не пов'язаних із мутантом (оточення, мережа). Тоді все виглядає вбитим. Якщо ворота підозріло зелені, подивіться лог `mutate-*.log`.

## Що від Мартіна, а що інакше

**Від Мартіна без змін:** текст `ub-mode` дослівно ([unclebob/ub-mode](https://github.com/unclebob/ub-mode), MIT; як він працює тут — `ub-kit.md` поруч); інструменти [crapper](https://github.com/unclebob/crapper), [dryer](https://github.com/unclebob/dryer), [mutator](https://github.com/unclebob/mutator) (0BSD) і [uml-viewer](https://github.com/unclebob/uml-viewer) — його ж, закріплені на комітах; пороги CRAP < 10, подібність 0,8, 0 мутантів; формат комітів Why / What / Proof; паралельні мутації (одне покриття, далі файли поруч); проходи за аспектами (`.ub/ub audit`); jitter-тести (`.ub/ub soak`); приймальні тести як окремий шар; керівний агент із субагентами (`/ub-lead`, за бажанням).

**Свідомо інакше:**

| | Мартін | ub-kit | Чому |
|---|---|---|---|
| Старий борг | агенти доводять до порогів увесь код | режим ratchet: червоне лише нове, старе — `DEBT` | інакше в наявному проєкті червона кожна задача; для нових — strict, як у нього |
| Приймальні тести | центр процесу (AgNesse) | необов'язкові: порожній `acceptance` — поведінку перевіряє людина | він сам допускає ручні перевірки; фреймворк обирає проєкт |
| Рецензія | у листопаді — керівний бот | `.ub/ub review` іншою моделлю на кожну задачу (його жовтнева практика) | одна команда, що працює і без оркестрації |
| Ослаблений тест | окремої перевірки нема | червоне, якщо вбитий раніше мутант тепер виживає | дешевий запобіжник від підгонки тестів |
| Захист воріт | дисципліна й нагляд | правки `.ub/`, скілів, `.metrics/` питають власника; ворота падають «закрито» | агенти підганяють результат — він сам про це писав |
| uml-viewer | разом із Grok-компаньйоном | лише діаграма і підрахунок порушень у воротах | компаньйона можна запустити його ж `get-uml-viewer` |

Інструменти й uml-viewer kit не містить: він клонує їх у `~/.cache/ub-kit` під їхніми власними ліцензіями. У uml-viewer ліцензії немає; етап діаграми опційний — без Java ворота його пропускають.
