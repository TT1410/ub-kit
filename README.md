# ub-kit

Метод Роберта Мартіна (жовтень 2026), який ставиться в будь-який репозиторій однією командою:
- одна задача — один дисциплінований агент зі скілом `ub-mode`;
- детерміновані ворота з інструментів Мартіна: crapper, dryer, mutator і uml-viewer;
- рецензія іншою моделлю;
- людина перевіряє поведінку руками і погоджує злиття.

Kit нічого не знає про вашу архітектуру. Він міряє код на Python, Go чи TypeScript, а шари й межі задаєте ви.

## Швидкий старт

```bash
~/Projects/GitHub/ub-kit/install.sh ~/Projects/my-repo      # наявний репозиторій, новий або порожня тека
cd ~/Projects/my-repo && claude                              # далі в Claude Code: /ub-setup
```

**`install.sh`** визначає й записує:
- мови та їхні корені;
- головну гілку;
- команду verify;
- режим.

Чого визначити не може, позначає `TODO(ub-setup)`. Ще він дописує рядок у justfile, блок у `AGENTS.md`/`CLAUDE.md`, правила «спитати власника» в `.claude/settings.json` і рядки в `.gitignore`. Нічого не комітить. Ключ `--dry-run` лише показує, що зміниться.

**`/ub-setup`** — скіл, який агент виконує разом із вами один раз:
- **новий проєкт:** питає мову, стек і шари й ставить мінімальний каркас під вашу відповідь;
- **наявний проєкт:** налаштовує verify і межі модулів, підключає плагін для vitest, записує шари на діаграмі й базову лінію боргу;
- **наприкінці** проганяє ворота на пробній зміні.

### Цикл кожної задачі

1. Ви ставите задачу. Агент працює за `ub-mode` на гілці задачі.
2. `just gate` має бути зеленим. Агент сам повторює його, доки не стане зеленим.
3. `just review`: інша модель читає дифф. Агент відповідає на кожне зауваження.
4. Ви перевіряєте поведінку руками й читаєте критичний код: гроші, безпеку.
5. Злиття. Push — лише за вашим словом.

Самі інструменти лежать поза репозиторієм, у спільному кеші `~/.cache/ub-kit/`. Їх клонують один раз на всі проєкти, на закріплених комітах:
- crapper, mutator і dryer — у Мартіна;
- uml-viewer — у форку TT1410 із Go-сканером.

## Ворота (`just gate [BASE]`)

Ворота судять тільки те, що змінилося від merge-base з головною гілкою, разом із незакоміченими файлами. Етапи:
1. **verify** — lint, типи, межі модулів, тести: команда з `.ub/config`.
2. **CRAP < 10** для функцій змінених файлів (crapper). Покриття беруть з тестів змінених пакетів чи модулів.
3. **Дублікати** з подібністю ≥ 0,8, що зачіпають зміну (dryer).
4. **Мутанти** не мають ні виживати, ні лишатися непокритими (mutator). Якщо змінилися тести, повністю мутується й код, який вони тестують. Мутант, якого раніше вбивали, а тепер він виживає, — завжди червоне. Знімок для порівняння береться з коміту бази, тож повторний запуск це не «відмиє».
5. **Dependency Rule** на діаграмі uml-viewer, якщо є політика, Java 21 і Clojure.

Ворота падають «закрито»: якщо інструмент упав, не дав звіту або нема чого судити — це червоне. `GATE_SKIP=verify,crap,dry,mutation,structure` пропускає етапи, але це записується в `.ub/out/gate/summary.txt`, і рецензент це бачить.

### Режими

- **strict** — для нових проєктів. Усе у змінених файлах має бути чистим.
- **ratchet** — для наявних проєктів. Червоне лише нове:
  - мутанти на змінених рядках;
  - дублікати, що зачіпають змінені рядки;
  - функції з CRAP ≥ 10, яких немає в базовій лінії або які погіршилися.

  Старий борг у зачеплених файлах іде у звіт рядками `DEBT:` і не блокує. Агент має лишити його меншим, ніж знайшов. Базову лінію записує `just ub-baseline`, з вашого дозволу.

Нові проєкти (до 15 файлів коду) отримують strict, решта — ratchet. Режим змінюється в `.ub/config`.

## Налаштування (`.ub/config`)

| Ключ | За замовчуванням | Що задає |
|---|---|---|
| `[ub] main` | визначається | гілка, від якої рахується зміна |
| `mode` | strict / ratchet | див. вище |
| `verify` | `just verify` | lint, типи, межі, тести, з кореня репозиторію |
| `crap_max`, `dry_threshold` | 10, 0.8 | пороги Мартіна |
| `exclude` | — | regex шляхів, які ворота не судять (згенерований код без заголовка «do not edit») |
| `structure` | auto | `off` вимикає етап діаграми |
| `workers` | 4 | паралельні мутанти на файл |
| `reviewers` | `grok codex` | порядок рецензентів. Якщо один не відповів, пробується наступний. `claude` — лише коли автор не Claude |
| `[python] root`, `src`, `test`, `coverage`, `setup` | | корінь, вихідний код, команди mutator і crapper, підготовка (наприклад, тестова БД) |
| `[go] root`, `src`, `tree`, `test`, `setup` | | `tree` — regex: група 1 — тека, чиї тести судять файл (модуль цілком) |
| `[typescript] root`, `src`, `setup` | | лише vitest |

## Мови

- **Python.** crapper і mutator самі запускають pytest із покриттям через `.venv`. Проєкт **не можна** ставити в `.venv` як editable: тоді тести бачать оригінал, а не копію mutator, і всі мутанти «виживають». З uv це `[tool.uv] package = false` плюс pytest `pythonpath = ["src"]`. `just ub-doctor` перевіряє це.
- **Go.** Покриття змінених пакетів. Шляхи у профілі переписуються з імені модуля на теку, тож модуль може називатися інакше, ніж його тека. Тести з БД запускаються через `[go] setup`.
- **TypeScript.** vitest і `@vitest/coverage-v8`. Специфікація лежить поруч із модулем (`name.spec.ts`, `name.test.ts` або `__tests__/`). У конфіг vitest треба вставити плагін `.ub/snippets/vitest-mutator-overlay.ts.txt`: Vite іде за симлінками mutator до оригіналу. Без плагіна ворота червоні з поясненням. vitest запускається власним бінарником, а не через `pnpm exec`: менеджер пакетів у копії mutator може перевстановлювати залежності й «вбивати» кожного мутанта.

## Вимоги

- git і Python ≥ 3.9 для kit; Python ≥ 3.11 на PATH для інструментів Мартіна;
- just;
- для своїх мов — uv, poetry чи pip; go; node з менеджером пакетів;
- для діаграми — Java 21 і Clojure CLI;
- для рецензії — Grok із кредитами або Codex після `codex login`.

`just ub-doctor` показує, чого бракує.

## Обмеження

- Ворота судять один корінь на мову. Якщо в монорепозиторії знайшлося кілька, інсталятор їх перелічує.
- `.vue`, `.svelte` і Gherkin ворота не судять. Їх перевіряє лише verify.
- mutator тримає знімок Go по одному на пакет. Регресію ослабленого тесту ворота ловлять для файлу, який мутувався останнім.
- Фальшиві «вбивства» можливі, якщо тест падає з причин, не пов'язаних із мутантом (оточення, мережа). Тоді все виглядає вбитим. Якщо ворота підозріло зелені, подивіться лог `mutate-*.log`.

## Як прибрати

Видаліть `.ub/` і `.claude/skills/ub-*`. Потім приберіть:
- рядок `import '.ub/ub.just'` (або `mod ub`) з justfile;
- блок `ub-kit` з `AGENTS.md`/`CLAUDE.md`;
- рядки `# ub-kit` з `.gitignore`;
- правила `ask` для `.ub/**` з `.claude/settings.json`.
